# youweiAI-amazon-场景-从竞品差评找产品改进点

## ★ 必填项与追问（强制执行，优先于下文任何“缺参数就问一次”的表述）


### 必填项
站点；1-3 个竞品 ASIN 或链接


### 可选/可默认项（缺了就按“未限定”处理，并在报告数据缺口里注明，不代填、不追问第二遍）
关注维度（产品/物流/包装）


### 追问方式（ask_user 表单，缺1项问1题）
一次性收齐所有缺的必填项，不要挤牙膏；已答不重问。ask_user 必须单独调用（不与 view_skill/业务工具并发），每题显式写 id（同次调用唯一）、2–3 个 options 且每项含 label+description，需要自由输入设 allow_other=true（写在 question 对象内）。选项给可直接点的具体候选（如站点：美国站/德国站/日本站；类目：真实子类名2-3个+其他）。用户说"你看着办"时取最保守口径并在报告口径段声明假设；收到回答直接继续任务，不复述不二次确认。

### 报告收尾必带"下一步引导"
结论区后给 2–3 条可直接复制的下一步（如「要不要把差评拉出来看改进点？（场景19）」「要不要图搜1688拿货价？（场景14）」），只给可点文字建议，不开 ask_user。

## 触发（本场景技能，执行时按需调用已绑定的公共技能与工具）
- 原始问法：我准备开发[产品]，想先知道同类产品被买家骂在哪。帮我看看这几个竞品（[ASIN1][ASIN2][ASIN3]）的1-3星差评：归类排序+摘原话→区分产品问题vs物流/描述→判断新起还是长期→整理成改进清单拿去和工厂谈
- 变体问法按语义匹配本场景；用户未给站点先问一次站点。

### 报告固定结构（自上而下）
1. **页头**：场景名 + 站点 + 查询日 + 证据口径标签（例："采样2页 · 去重后14款 · 详情已核9款"）。
2. **KPI 卡行**：3~5 张卡，每卡 = 大数字 + 指标名 + 口径小字。
3. **明细表**：按本场景规定排序。商品行首列「主图+ASIN 同格」；关键词、类目、供应商、广告搜索词等非商品行使用对应对象名作首列，不虚构 ASIN、主图或商品链接。其后只列本场景所需字段。
4. **结论/建议区**：分档结论、可选方向、风险与红线；每条结论后标注依据字段。
5. **数据缺口与口径声明**：缺字段、降级口径、异常值、样本非全量，逐条列明。
6. **溯源**：本轮接口任务查看链接（<a target="_blank">），便于核对原始返回。

## 原始场景口径（业务目标与阈值依据）
下文是场景表原文，包含历史工具名、示例及旧执行建议；与本技能的「执行步骤」「公共纪律」冲突时以后两者为准。原文中的降档只用于另列诊断结果，不能放宽严格达标口径；没有真实字段时标为不可判定。
分析Amazon美站竞品差评（[ASIN1][ASIN2][ASIN3]），为开发[产品]提供改进依据：
1. 逐品拆解（不做汇总）：每竞品=主图+档案（价格/月销/评论数）+差评逐条归属（星级/日期/原话+中文翻译——每条差评引文必须紧跟中文翻译，用户要求）
2. 差评归类：按出现次数排序，每类摘2-3条原话（每条附中文翻译）
3. 归属判定：产品本身（工厂QC可修）vs 物流/描述不符（Listing可修）
4. 时间分布：最近才多起来 vs 一直都有（按review_date聚合）
5. 数据缺失双查纪律：详情接口review_count与列表接口实际返回分别核验——『没有评论』与『接口抓不到』是两个事实，必须分开写；变体家族（评论聚合在父体）导致的列表缺失要注明成因
6. 改进清单：按P0/P1排序+给工厂的一句话需求（规格+成本红线）
7. 可选延伸：哪款更适合作为开发基准+切入点（价差/配置/质量三重错位分析）
数据源：卖家精灵 product_detail + product_content + product_reviews
8. 报告呈现纪律（2026-11-12用户反馈）：差评原文必须每条配中文翻译；某竞品评论列表拉不到时（如变体家族聚合父体页），用sorftime买家之声兜底核验后直接展示最终结论，不在正文展示"卖家精灵拉不到→sorftime补测"的接口过程——过程细节只留footer数据口径一行；报告页不显示数据源标识（不出现"数据源：卖家精灵/sorftime"等工具名badge或文案，接口名也不入正文——工具信息只留给执行层）
9. 数据准确性纪律（2026-11-12用户质询修正）：①总评论数=各竞品详情接口review_count实拉求和（本次实拉A83+B35+C153=271条，此前320条为翻页去重口径错误）；②评分字段必须实拉补齐——报告严禁出现「⭐None」字样，接口返回空时换搜索接口二次实拉（collect_amazon_search的score字段）；③1-3星差评少是正常现象（4.6-4.8分商品差评率1-3%），统计卡必须注明差评占总评比例让数据自解释；④商品档案必须逐字段分行展示（价格/月销/评分/评论数/上架/配置各占一行，灰标签+数值），禁止「$46.99｜月销1273｜评79条｜⭐None」式挤压串行；⑤差评引文与翻译条间距≥8px、行高≥1.8倍，保证长文本完整展示不重叠

## 执行步骤
1. 确认竞品ASIN与差评范围（默认1-3星）；逐条抓取并按问题类型聚类（质量/尺寸/功能/物流/描述不符）。
2. 统计每类占比与代表原文（摘录带日期），对比竞品间差异。
3. 输出：问题聚类表（类型｜占比｜代表摘录）+改进建议（可落地项优先）+成本提示。
4. 样本量写明（总评论数/差评数/已读数），不推全。

## 公共纪律与异常（详版见 youweiai-amazon-report-gen，不可豁免）
- 空值不补零，缺失标"未取得"；真实0与缺失分开；总命中≠样本，样本不推全市场并披露覆盖率。
- 表格每个数字溯源到本轮接口返回；严格0条不造表，放宽诊断单列标"诊断"。
- 502/504 如实记"环境异常"或走降级通道，不写成通过；execute_code 只1次机会，同参重复调用即熔断改人工核算；ask_user pending 时不得对该会话 API 续跑。

## ★ 深度交付层（对照运营报告骨架，优先于简化输出）
运营实测报告（麻将牌收纳包三竞品版）已验证本场景的完整交付形态：

1. **逐竞品专节**：每竞品一节=定价+月销+评分/评论总数（实拉口径标注）+1-3星差评抓取数+上架日期+配置差异+逐条差评表（星级｜日期｜原话+中文翻译）；竞品定位一句概括（如"差评最重，品质问题全集中在它"）。
2. **接口受限如实标注**：变体家族评论聚合父体页的竞品用买家之声兜底（话题正负提及数），不冒充评论列表；过程归footer。
3. **三款横向对比表**：维度=价格｜月销｜评分/评论｜配置｜差评主题｜趋势方向；倒挂现象点名（如"B配置少一件却$49.99定价倒挂"）。
4. **切入结论节**：以哪款为配置基准+以哪款为质量反例+卡位价格带（如"$32-36错位切入"）+改进清单P0排序（给工厂的一句话需求：规格+成本红线）。
